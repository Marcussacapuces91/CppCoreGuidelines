# <a name="s-not"></a>NR : Non‑Règles et Mythes

Cette section contient des règles et directives qui sont populaires quelque part, mais que nous ne recommandons délibérément pas.  
Nous savons parfaitement qu’il existe des périodes et des contextes où ces règles avaient du sens, et nous les avons utilisées nous‑mêmes à certains moments.  
Cependant, dans le cadre des styles de programmation que nous recommandons et soutenons par le biais de ces lignes directrices, ces « non‑règles » sont préjudiciables.  

Aujourd’hui encore, il existe des contextes où les règles peuvent avoir du sens.  
Par exemple, l’absence de support d’outils adaptés peut rendre les exceptions inadaptées dans les systèmes temps réel stricts, mais ne faites pas naïvement confiance à la « sagesse populaire » (par ex. des affirmations non étayées concernant l’« efficacité »).  
Cette « sagesse » peut être fondée sur des informations d’antan ou des expériences issues de langages très différents du C++ (par exemple, C ou Java).  

Les arguments positifs proposant des alternatives à ces non‑règles sont listés dans les règles proposées comme « Alternatives ».

### <a name="rnr-top"></a>NR.1 : Ne pas insister sur le fait que toutes les déclarations doivent se trouver en haut d’une fonction  

#### Raisonnement  

La règle « toutes les déclarations en haut » provient de vieux langages de programmation qui ne permettaient pas l’initialisation de variables et de constantes après une instruction.  
Cela conduit à des programmes plus longs et à davantage d’erreurs dues à des variables non initialisées ou mal initialisées.  

#### Exemple – mauvais  

    int use(int x)
    {
        int i;
        char c;
        double d;

        // ... du code ...

        if (x < i) {
            // ...
            i = f(i, d);
        }
        if (i < x) {
            // ...
            i = g(i, c);
        }
        return i;
    }

Plus la distance entre une variable non initialisée et son utilisation est grande, plus le risque d’erreur augmente.  
Heureusement, les compilateurs détectent de nombreuses erreurs « utilisé avant d’être configuré ».  
Malheureusement, ils ne peuvent pas détecter toutes les erreurs et, de plus, les bogues ne sont pas toujours aussi simples à repérer que dans cet exemple.

### <a name="rnr-single-return"></a>NR.2 : Ne pas insister sur le fait d’avoir uniquement une seule instruction `return` dans une fonction  

#### Raisonnement  

La règle d’unicité du retour peut conduire à un code inutilement complexe et à l’introduction de variables d’état supplémentaires.  
En particulier, elle rend plus difficile la concentration de la vérification d’erreurs en haut de la fonction.  

#### Exemple  

    template<class T>
    //  nécessite Number<T>
    string sign(T x)
    {
        if (x < 0)
            return "negative";
        if (x > 0)
            return "positive";
        return "zero";
    }

Pour n’utiliser qu’un seul retour, il faudrait faire quelque chose comme  

    template<class T>
    //  nécessite Number<T>
    string sign(T x)        // mauvais
    {
        string res;
        if (x < 0)
            res = "negative";
        else if (x > 0)
            res = "positive";
        else
            res = "zero";
        return res;
    }

Ceci est plus long et probablement moins efficace.  
Plus la fonction est grande et complexe, plus les solutions de contournement deviennent pénibles.  
Bien sûr, de nombreuses fonctions simples n’auront naturellement qu’un seul `return` à cause de leur logique plus simple.  

#### Exemple  

    int index(const char* p)
    {
        if (!p) return -1;  // indicateur d’erreur : alternativement « throw nullptr_error{} »
        // ... faire une recherche pour trouver l’index de p
        return i;
    }

Si l’on appliquait la règle, on obtiendrait quelque chose comme  

    int index2(const char* p)
    {
        int i;
        if (!p)
            i = -1;  // indicateur d’erreur
        else {
            // ... faire une recherche pour trouver l’index de p
        }
        return i;
    }

Notez que nous (délibérément) avons violé la règle contre les variables non initialisées car ce style conduit généralement à cela.  
De plus, ce style est une tentation d’utiliser le non‑règle [goto exit](#rnr-goto-exit).  

#### Alternative  

* Gardez les fonctions courtes et simples  
* N’hésitez pas à utiliser plusieurs instructions `return` (et à lancer des exceptions).  

### <a name="rnr-no-exceptions"></a>NR.3 : Ne pas éviter les exceptions  

#### Raisonnement  

Il semble y avoir quatre raisons principales pour ne pas utiliser d’exceptions :  

* les exceptions sont inefficaces  
* les exceptions entraînent des fuites et des erreurs  
* la performance des exceptions n’est pas prévisible  
* le support d’exécution des exceptions prend trop de place  

Il n’existe aucun moyen de satisfaire tout le monde sur ce sujet.  
Après tout, les discussions sur les exceptions se poursuivent depuis plus de quarante ans.  
Certains langages ne peuvent pas être utilisés sans exceptions, d’autres ne les prennent pas en charge.  
Cela crée des traditions fortes pour l’usage ou l’abstention des exceptions, ainsi que des débats houleux.  

Cependant, nous pouvons énumérer brièvement pourquoi nous considérons les exceptions comme la meilleure alternative pour la programmation générale et dans le contexte de ces lignes directrices.  
Les arguments simples pour et contre sont souvent inconclusifs.  
Il existe des applications spécialisées où les exceptions peuvent effectivement être inappropriées (par ex. les systèmes temps réel stricts sans prise en charge fiable des estimations du coût d’une gestion d’une exception).  

Examinons les objections majeures aux exceptions, une par une :  

* Les exceptions sont inefficaces :  
  Comparées à quoi ?  
  Lorsque vous comparez, assurez‑vous que la même série d’erreurs est traitée et qu’elles le sont de façon équivalente.  
  En particulier, ne comparez pas un programme qui termine immédiatement dès qu’il détecte une erreur avec un programme qui nettoie soigneusement les ressources avant de consigner une erreur.  
  Oui, certains systèmes ont de mauvaises implémentations de la gestion d’exceptions ; parfois, ces implémentations nous obligent à utiliser d’autres approches de gestion d’erreurs, mais ce n’est pas un problème fondamental des exceptions.  
  Quand vous utilisez un argument d’efficacité — dans n’importe quel contexte — soyez prudent quant à disposer de bonnes données qui offrent réellement un aperçu du problème en discussion.  
* Les exceptions entraînent des fuites et des erreurs.  
  Cela n’est pas vrai.  
  Si votre programme est un amas de pointeurs sans une stratégie globale de gestion des ressources, vous avez un problème quoi que vous fassiez.  
  Si votre système contient un million de lignes de ce type de code, vous ne pourrez probablement pas utiliser d’exceptions, mais cela résulte d’un usage excessif et imprégné de pointeurs, pas d’une mauvaise gestion des exceptions.  
  À notre avis, vous avez besoin de RAII pour rendre la gestion d’erreur basée sur les exceptions simple et sûre — plus simple et plus sûre que les alternatives.  
* La performance des exceptions n’est pas prévisible.  
  Si vous êtes dans un système temps réel strict où vous devez garantir la complétion d’une tâche dans un temps donné, vous avez besoin d’outils pour soutenir de telles garanties.  
  À ce qui nous paraît, ces outils ne sont pas disponibles (du moins pas aux programmeurs réguliers).  
* Le support d’exécution de la gestion d’exceptions prend trop de place.  
  Cela peut être le cas dans les petits systèmes (généralement embarqués).  
  Cependant, avant d’abandonner les exceptions, considérez combien d’espace serait nécessaire pour un traitement d’erreurs cohérent utilisant des codes d’erreur et quel serait le coût de ne pas attraper une erreur.  

Beaucoup, voire la plupart, des problèmes liés aux exceptions proviennent des besoins historiques d’interagir avec un ancien code encombré.  

Les arguments fondamentaux en faveur de l’utilisation des exceptions sont :  

* Elles différencient clairement un retour erroné d’un retour ordinaire  
* Elles ne peuvent pas être oubliées ou ignorées  
* Elles peuvent être utilisées de façon systématique  

Souvenez‑vous :  

* Les exceptions servent à signaler des erreurs (en C++, d’autres langages peuvent avoir des usages différents).  
* Les exceptions ne servent pas aux erreurs pouvant être traitées localement.  
* Ne tentez pas d’attraper chaque exception dans chaque fonction (c’est fastidieux, maladroit et ralentit le code).  
* Les exceptions ne servent pas aux erreurs nécessitant une terminaison instantanée d’un module/système après une erreur non récupérable.

### <a name="rnr-lots-of-files"></a>NR.4 : Ne pas insister sur le fait de placer chaque définition de classe dans son propre fichier source  

#### Raisonnement  

Le nombre de fichiers résultant de la séparation de chaque classe dans son propre fichier est difficile à gérer et peut ralentir la compilation.  
Les classes individuelles ne constituent rarement une unité logique de maintenance et de distribution efficace.

### <a name="rnr-two-phase-init"></a>NR.5 : Ne pas utiliser l’initialisation en deux phases  

#### Raisonnement  

Diviser l’initialisation en deux phases entraîne des invariants plus faibles, du code plus compliqué (doit gérer des objets partiellement construits) et des erreurs (lorsqu’on ne traite pas correctement les objets partiellement construits de façon cohérente).  

#### Remarque  

On l’appelle parfois également construction en deux étapes.  

#### Exemple – mauvais  

    // Ancien style conventionnel : nombreux problèmes

    class Picture
    {
        int mx;
        int my;
        int * data;
    public:
        // Problème principal : le constructeur ne construit pas entièrement
        Picture(int x, int y)
        {
            mx = x;         // Mauvais : assignation dans le corps du constructeur
                            // plutôt que dans l’initialiseur de membre
            my = y;
            data = nullptr; // Mauvais : initialisation constante dans le constructeur
                            // plutôt que dans l’initialiseur de membre
        }

        ~Picture()
        {
            Cleanup();
        }

        // ...

        // Mauvaise : initialisation en deux phases
        bool Init()
        {
            // Vérification d’invariant
            if (mx <= 0 || my <= 0) {
                return false;
            }
            if (data) {
                return false;
            }
            data = (int*) malloc(mx*my*sizeof(int));   // Mauvais : pointeur brut et malloc propriétaire
            return data != nullptr;
        }

        // Mauvais : aucune raison de séparer le nettoyage dans une fonction distincte
        void Cleanup()
        {
            if (data) free(data);
            data = nullptr;
        }
    };

    Picture picture(100, 0); // pas encore prêt à l’emploi
    // cela échouera…
    if (!picture.Init()) {
        puts("Error, invalid picture");
    }
    // on possède maintenant un objet Picture invalide.  

#### Exemple – bon  

    class Picture
    {
        int mx;
        int my;
        vector<int> data;

        static int check_size(int size)
        {
            // vérification d'invariant
            Expects(size > 0);
            return size;
        }

    public:
        // mieux serait une classe pour une taille 2D comme un seul paramètre
        Picture(int x, int y)
            : mx(check_size(x))
            , my(check_size(y))
            // nous savons maintenant que x et y ont une taille valide
            , data(mx * my) // lèvera std::bad_alloc en cas d'erreur
        {
            // l’image est prête à l'emploi
        }

        // le destructor généré par le compilateur fait le travail (voir aussi C.21)

        // ...
    };

    Picture picture1(100, 100);
    // l'image picture1 est prête à l'emploi ici...

    // ce n'est pas une taille valide pour y,
    // le comportement par défaut en cas de violation de contrat appellera std::terminate alors
    Picture picture2(100, 0);
    // ne sera pas atteint ici...  

#### Alternative  

* Toujours établir un invariant de classe dans le constructeur.  
* Ne pas définir un objet avant qu’il ne soit nécessaire.  

### <a name="rnr-goto-exit"></a>NR.6 : Ne pas placer toutes les actions de nettoyage à la fin d’une fonction et utiliser `goto exit`  

#### Raisonnement  

`goto` est source d’erreurs.  
Cette technique constitue une approche « pré‑exceptions » pour la gestion des ressources et des erreurs similaire à RAII.  

#### Exemple – mauvais  

    void do_something(int n)
    {
        if (n < 100) goto exit;
        // ...
        int* p = (int*) malloc(n);
        // ...
        if (some_error) goto exit;
        // ...
    exit:
        free(p);
    }

et repérez le bogue.  

#### Alternative  

* Utiliser les exceptions et [RAII](#re-raii) @TODO-LINK  
* pour les ressources non‑RAII, utilisez [finally](#re-finally) @TODO-LINK  

### <a name="rnr-protected-data"></a>NR.7 : Ne pas rendre les membres de données `protected`

Les données `protected` sont une source d’erreurs.  
Les données `protected` peuvent être manipulées depuis un nombre illimité de code dans divers endroits.  
Les données `protected` sont l’équivalent de l’héritage hiérarchique des données globales.
