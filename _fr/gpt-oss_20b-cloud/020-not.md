# <a name="s-not"></a>NR : Non-règles et mythes

Cette section contient des règles et des lignes directrices qui sont populaires quelque part, mais que nous ne recommandons délibérément pas.
Nous savons parfaitement qu'il a existé, à certains moments et dans certains contextes, des situations où ces règles avaient du sens, et nous les avons parfois utilisées nous-mêmes.
Cependant, dans le contexte des styles de programmation que nous recommandons et soutenons avec ces lignes directrices, ces « non-règles » causeraient du tort.

Et même aujourd'hui, il peut y avoir des contextes où les règles ont du sens.
Par exemple, l'absence de support d'outils appropriés peut rendre les exceptions inadaptées dans les systèmes à temps réel strict,
mais ne faites pas naïvement confiance à la « sagesse commune » (par ex. les affirmations non supportées sur l'« efficacité »);
cette « sagesse » peut être fondée sur des informations vieillissantes ou sur des expériences de langages très différents de C++
(tels que C ou Java).

Les arguments positifs pour les alternatives à ces non-règles sont énumérés dans les règles proposées comme « Alternatives ».

### <a name="rnr-top"></a>NR.1 : Ne pas insister que toutes les déclarations soient en haut d'une fonction

##### Raison

La règle « toutes les déclarations en haut » est un héritage des anciens langages de programmation qui ne permettaient pas d'initialiser les variables et constantes après une instruction.
Cela conduit à des programmes plus longs et à des erreurs plus nombreuses causées par des variables non initialisées ou mal initialisées.
Plus la distance entre la variable non initialisée et son utilisation est grande, plus la probabilité d'une erreur augmente.
Heureusement, les compilateurs détectent beaucoup d'erreurs de type « utilisé avant initialisé ».
Malheureusement, les compilateurs ne peuvent pas détecter toutes ces erreurs et, en plus, les bugs ne sont pas toujours aussi faciles à repérer que dans cet exemple réduit.

##### Alternatives

* [Toujours initialiser un objet](010-expr.md#res-always)
* [ES.21 : Ne pas introduire une variable (ou constante) avant de l'utiliser](010-expr.md#res-introduce)

### <a name="rnr-single-return"></a>NR.2 : Ne pas insister sur le fait d'avoir un seul `return`‑statement dans une fonction

##### Raison

La règle du unique `return` peut entraîner un code inutilement compliqué et l'introduction de variables d'état supplémentaires.
En particulier, la règle du unique `return` rend plus difficile de concentrer la vérification des erreurs en haut d'une fonction.

##### Exemple

    template<class T>
    // requiert Number<T>
    string sign(T x)
    {
        if (x < 0)
            return "negative";
        if (x > 0)
            return "positive";
        return "zero";
    }

Pour n'utiliser qu'un seul `return`, il faudrait quelque chose comme

    template<class T>
    // requiert Number<T>
    string sign(T x)        // mauvais
    {
        string res;
        if (x < 0)
            res = "negative";
        else if (x > 0)
            res = "positive";
        else
            res = "zero";
        return res;
    }

Ceci est à la fois plus long et probablement moins efficace.
À mesure qu'une fonction devient plus grande et plus compliquée, les solutions de contournement deviennent plus douloureuses.
Bien sûr, de nombreuses fonctions simples auront naturellement un seul `return` en raison de leur logique intrinsèque.

##### Exemple

    int index(const char* p)
    {
        if (!p) return -1;  // indicateur d'erreur : alternativement "throw nullptr_error{}"
        // ... faire une recherche pour trouver l'index de p
        return i;
    }

Si nous appliquions la règle, nous obtiendrions quelque chose comme

    int index2(const char* p)
    {
        int i;
        if (!p)
            i = -1;  // indicateur d'erreur
        else {
            // ... faire une recherche pour trouver l'index de p
        }
        return i;
    }

Notez que nous violons délibérément la règle contre les variables non initialisées parce que ce style conduit généralement à cela.
Cette approche est aussi une tentation d'utiliser le non-règle [goto exit].

##### Alternatives

* Gardez les fonctions courtes et simples
* N'hésitez pas à utiliser plusieurs `return` (et à lancer des exceptions)

### <a name="rnr-no-exceptions"></a>NR.3 : Ne pas éviter les exceptions

##### Raison

Il semble y avoir quatre raisons principales invoquées pour ne pas utiliser d'exceptions :

* les exceptions sont inefficaces
* les exceptions entraînent les fuites et les erreurs
* la performance des exceptions n'est pas prévisible
* le support d'exécution pour la gestion des exceptions prend trop d'espace

Il n'est pas possible de régler cette question à la satisfaction de tout le monde.
Après tout, les discussions autour des exceptions se poursuivent depuis plus de 40 ans.
Certains langages ne peuvent pas être utilisés sans exceptions, tandis que d'autres ne les prennent pas en charge.
Cela entraîne de fortes traditions d'utilisation ou de non‑usage des exceptions, ainsi que des débats vifs.

Cependant, nous pouvons brièvement expliquer pourquoi nous considérons les exceptions comme la meilleure alternative pour la programmation généraliste dans le cadre de ces lignes directrices.
Les arguments simples pour et contre sont souvent sans conclusion.
Il existe des applications spécialisées où les exceptions peuvent vraiment être inappropriées (par ex., les systèmes à temps réel strict sans prise en charge des estimations fiables du coût du traitement d'une exception).

Considérons les principales objections aux exceptions :

* **Les exceptions sont inefficaces** : comparées à quoi ? Lorsqu'on compare, assurez‑vous que le même ensemble d'erreurs est géré et qu'il l'est de façon équivalente.
En particulier, ne comparez pas un programme qui s'arrête immédiatement en cas d'erreur à un programme qui nettoie soigneusement les ressources avant d'enregistrer l'erreur.
Oui, certains systèmes ont de mauvaises implémentations de gestion des exceptions ; parfois, de telles implémentations nous forcent à utiliser d'autres approches de gestion des erreurs, mais ce n'est pas un problème fondamental lié aux exceptions.
Lorsque vous utilisez un argument d'efficacité — dans n'importe quel contexte — faites attention que vous disposez de bonnes données qui donnent réellement un aperçu du problème discuté.
* **Les exceptions entraînent des fuites et des erreurs** : elles ne le font pas.
Si votre programme est un épilogue de pointeurs sans une stratégie globale de gestion des ressources, vous avez un problème quelle que soit votre approche.
Si votre système compte un million de lignes de ce type de code, vous ne pourrez probablement pas utiliser les exceptions,
mais c'est un problème d'utilisation excessive et non disciplinée de pointeurs, plutôt qu'un problème des exceptions.
À nos avis, vous avez besoin de RAII pour rendre la gestion d'erreurs basée sur des exceptions simple et sûre — plus simple et plus sûre que les alternatives.
* **La performance des exceptions n'est pas prévisible** : si vous êtes dans un système à temps réel strict où vous devez garantir la complétion d'une tâche dans un temps donné,
vous avez besoin d'outils pour étayer ces garanties.
En l'état actuel, ces outils ne sont pas disponibles (au moins pas pour la plupart des programmeurs).
* **Le support d'exécution pour la gestion des exceptions prend trop d'espace** : cela peut être le cas dans les petits systèmes (souvent embarqués).
Cependant, avant d'abandonner les exceptions, considérez le coût en espace d'un traitement d'erreurs cohérent par des codes d'erreur et le coût d'un faux négatif.

Les arguments fondamentaux en faveur de l'utilisation des exceptions sont :

* Elles différencient clairement un retour erroné d'un retour ordinaire
* Elles ne peuvent pas être oubliées ou ignorées
* Elles peuvent être utilisées systématiquement

N'oubliez pas :

* Les exceptions servent à signaler des erreurs (en C++ ; d'autres langages peuvent les utiliser à d'autres fins).
* Les exceptions ne servent pas à des erreurs qui peuvent être résolues localement.
* Ne tentez pas de capturer chaque exception dans chaque fonction (cela devient laborieux, maladroit et entraîne un code lent).
* Les exceptions ne servent pas à des erreurs qui nécessitent une terminaison instantanée d'un module/système après une erreur non récupérable.

### <a name="rnr-lots-of-files"></a>NR.4 : Ne pas insister sur le fait de placer chaque définition de classe dans son propre fichier source

##### Raison

Le nombre de fichiers résultant de la mise en place d'une classe dans son propre fichier est difficile à gérer et peut ralentir la compilation.
Les classes individuelles ne constituent rarement une bonne unité logique de maintenance et de distribution.

### <a name="rnr-two-phase-init"></a>NR.5 : Ne pas utiliser l'initialisation à deux phases

##### Raison

Diviser l'initialisation en deux entraîne de moins bons invariants, du code plus complexe (doit gérer des objets semi‑construits) et des erreurs (lorsque nous n'avons pas géré correctement les objets semi‑construits de façon cohérente).

##### Note

Également appelé construction en deux étapes.

##### Exemple, mauvais

    // Old conventional style: many problems
    class Picture
    {
        int mx;
        int my;
        int * data;
    public:
        // problème principal : le constructeur ne construit pas complètement
        Picture(int x, int y)
        {
            mx = x;         // mauvaise : assignation dans le corps du constructeur
                            // plutôt que dans l'initialiseur de membre
            my = y;
            data = nullptr; // mauvaise : initialisation constante dans le constructeur
                            // plutôt que dans l'initialiseur de membre
        }

        ~Picture()
        {
            Cleanup();
        }

        // ...

        // mauvaise : initialisation à deux phases
        bool Init()
        {
            // vérifications d'invariant
            if (mx <= 0 || my <= 0) {
                return false;
            }
            if (data) {
                return false;
            }
            data = (int*) malloc(mx*my*sizeof(int));   // mauvaise : ownership raw * et malloc
            return data != nullptr;
        }

        // mauvaise : pas de raison de séparer le nettoyage dans une fonction
        void Cleanup()
        {
            if (data) free(data);
            data = nullptr;
        }
    };

    Picture picture(100, 0); // pas encore prêt à l'emploi
    // cela échouera…
    if (!picture.Init()) {
        puts("Error, invalid picture");
    }
    // on a maintenant une instance d'objet invalide.

##### Exemple, bon

    class Picture
    {
        int mx;
        int my;
        vector<int> data;

        static int check_size(int size)
        {
            // vérification d'invariant
            Expects(size > 0);
            return size;
        }

    public:
        // même mieux serait une classe pour une taille 2D en un seul paramètre
        Picture(int x, int y)
            : mx(check_size(x))
            , my(check_size(y))
            // maintenant nous savons que x et y ont une taille valide
            , data(mx * my) // lèvera std::bad_alloc en cas d'erreur
        {
            // l'image est prête à l'emploi
        }

        // le destructeur généré par le compilateur fait le travail (voir aussi C.21)

        // ...
    };

    Picture picture1(100, 100);
    // picture1 est prêt à l'emploi ici...

    // taille non valide pour y,
    // le comportement par défaut en cas de violation de contrat appellera std::terminate ensuite
    Picture picture2(100, 0);
    // n'arrive pas ici...

##### Alternatives

* Établissez toujours un invariant de classe dans le constructeur.
* N'initialisez pas un objet avant qu'il soit nécessaire.

### <a name="rnr-goto-exit"></a>NR.6 : Ne pas regrouper toutes les actions de nettoyage à la fin d'une fonction et utiliser `goto exit`

##### Raison

`goto` est source d'erreurs. Cette technique est une technique pré‑exceptions pour la gestion de ressources RAII‑like et des erreurs.

##### Exemple, mauvais

    void do_something(int n)
    {
        if (n < 100) goto exit;
        // ...
        int* p = (int*) malloc(n);
        // ...
        if (some_error) goto exit;
        // ...
    exit:
        free(p);
    }

et repérez l'erreur.

##### Alternatives

* Utilisez les exceptions et [RAII](013-errors.md#re-raii)
* pour les ressources non‑RAII, utilisez `finally` (voir 013-errors.md#re-finally)

Les données `protected` sont une source d'erreurs.
Les données `protected` peuvent être manipulées par une quantité illimitée de code à divers endroits.
Les données `protected` sont l'équivalent de données globales dans la hiérarchie de classes.
