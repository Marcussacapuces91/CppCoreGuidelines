# <a name="s-gsl"></a>GSL: Bibliothèque de support des directives

Le GSL est une petite bibliothèque de fonctionnalités conçue pour soutenir cet ensemble de directives.  
Sans ces fonctionnalités, les directives devraient être beaucoup plus restrictives sur les détails du langage.

La bibliothèque de support des directives de base est définie dans l'espace de noms `gsl` et les noms peuvent être des alias pour les noms de la bibliothèque standard ou d'autres bibliothèques bien connues.  
L'utilisation de l'indirection (à la compilation) via l'espace de noms `gsl` permet l'expérimentation et des variantes locales des fonctionnalités de support.

Le GSL est uniquement en en-tête, et peut être trouvé sur [GSL: Bibliothèque de support des directives](https://github.com/Microsoft/GSL).  
Les fonctionnalités de la bibliothèque de support sont conçues pour être extrêmement légères (sans surcoût) afin qu'elles n'imposent aucun surcoût par rapport à l'utilisation d'alternatives conventionnelles.  
Lorsqu'il est souhaitable, elles peuvent être « instrumentées » avec des fonctionnalités supplémentaires (par ex., des vérifications) pour des tâches telles que le débogage.

Ces directives utilisent des types de la norme (par ex., C++17) en plus de ceux du GSL.  
Par exemple, nous supposons un type `variant`, mais celui-ci n'est pas encore présent dans le GSL.  
À terme, utilisez [celui qui a été voté dans C++17](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0088r3.html).

Certains des types GSL listés ci-dessous peuvent ne pas être pris en charge dans la bibliothèque que vous utilisez en raison de raisons techniques telles que les limitations des versions actuelles de C++.  
Par conséquent, veuillez consulter votre documentation GSL pour en savoir plus.

Pour chaque type GSL ci-dessous, nous indiquons une invariant pour ce type.  
Cette invariant est valable tant que le code utilisateur ne modifie l'état d'un objet GSL qu'en utilisant les fonctions membres/freely fournies par le type (c.-à-d., le code utilisateur ne contourne pas l'interface du type pour modifier la valeur/les bits de l'objet en violant une autre règle des directives).

## <a name="ss-views"></a>GSL.view: Vues

Ces types permettent à l'utilisateur de distinguer les pointeurs propriétaires et non propriétaires ainsi que les pointeurs vers un seul objet et les pointeurs vers le premier élément d'une séquence.

Ces « vues » ne sont jamais des propriétaires.

Les références ne sont jamais propriétaires (voir [R.4](009-resource.md#rr-ref) @TODO-LINK).  
Remarque : les références ont de nombreuses occasions de dépasser la durée de vie des objets auxquels elles se réfèrent (retourner une variable locale par référence, conserver une référence à un élément d'un vecteur et effectuer `push_back`, lier à `std::max(x, y + 1)`, etc.).  
Le profil de sécurité de durée de vie vise à résoudre ces problèmes, mais même ainsi `owner<T&>` n'a pas de sens et est déconseillé.

Les noms sont majoritairement dans le style de la bibliothèque standard ISO (minuscules et underscore) :

* `T*`      // Le `T*` n'est pas un propriétaire, peut être nul ; supposé pointer vers un seul élément.
* `T&`      // Le `T&` n'est pas un propriétaire et ne peut jamais être une « référence nulle » ; les références sont toujours liées à des objets.

La notation « pointeur brut » (par ex. `int*`) est supposée avoir sa signification la plus courante ; c'est-à-dire qu'un pointeur pointe vers un objet, mais ne le possède pas.

Les propriétaires devraient être convertis en gestionnaires de ressources (par ex. `unique_ptr` ou `vector<T>`) ou marqués `owner<T*>`.

    owner<T*>   // un `T*` qui possède l'objet pointé/référencé ; peut être `nullptr`.

`owner` est utilisé pour marquer les pointeurs propriétaires dans le code qui ne peut pas être mis à niveau pour utiliser des gestionnaires de ressources appropriés.  
Les raisons incluent :

* Coût de conversion.
* Le pointeur est utilisé avec une ABI.
* Le pointeur fait partie de l'implémentation d'un gestionnaire de ressources.

Un `owner<T>` diffère d'un gestionnaire de ressources pour un `T` en nécessitant toujours un `delete` explicite.

Un `owner<T>` est supposé référer à un objet sur le tas (heap).

Si quelque chose ne doit pas être `nullptr`, indiquez-le :

* `not_null<T>`   // `T` est généralement un type pointeur (par ex. `not_null<int*>` et `not_null<owner<Foo*>>`) qui ne doit pas être `nullptr`. `T` peut être n'importe quel type pour lequel `==nullptr` a du sens.
* `span<T>`       // `[p:p+n)`, constructeur à partir de `{p, q}` et `{p, n}` ; `T` est le type pointeur
* `span_p<T>`     // `{p, predicate}` `[p:q)` où `q` est le premier élément pour lequel `predicate(*p)` est vrai

Un `span<T>` fait référence à zéro ou plusieurs `T` mutables à moins que `T` ne soit un type `const`.  
Tous les accès aux éléments du span, notamment via `operator[]`, sont garantis d'être vérifiés par défaut.

> Remarque : le `span` du GSL (initialement appelé `array_view`) a été proposé pour inclusion dans la bibliothèque standard C++, et a été adopté (avec des modifications de son nom et de son interface) à l'exception du fait que `std::span` ne fournit pas de vérification des limites garantie.  
> Par conséquent, le GSL a changé le nom et l'interface de `span` pour suivre `std::span` et devrait être exactement le même que `std::span`, et la seule différence devrait être que le `span` du GSL est entièrement sûr par défaut.  
> Si la sûreté des limites peut affecter son interface, alors ces propositions de changement devraient être réintroduites via le comité ISO C++ pour maintenir l'interface `gsl::span` compatible avec `std::span`.  
> Si une évolution future de `std::span` ajoute la vérification des limites, `gsl::span` peut être supprimé.

L'arithmétique des pointeurs est mieux effectuée au sein des `span`.  
Un `char*` qui pointe vers plus d'un `char` mais n'est pas une chaîne de caractères C (par ex., un pointeur dans un tampon d'entrée) devrait être représenté par un `span`.

* `zstring`    // un `char*` supposé être une chaîne de caractères C ; c'est-à-dire une séquence terminée par zéro de `char` ou `nullptr`
* `czstring`   // un `const char*` supposé être une chaîne de caractères C ; c'est-à-dire une séquence terminée par zéro de `const` `char` ou `nullptr`

Logiquement, ces deux alias ne sont pas nécessaires, mais nous ne sommes pas toujours logiques, et ils rendent explicite la distinction entre un pointeur vers un `char` et un pointeur vers une chaîne de caractères C.  
Une séquence de caractères qui n'est pas supposée être terminée par zéro devrait être un `span<char>`, ou si cela est impossible en raison de problèmes d'ABI un `char*`, plutôt qu'un `zstring`.

## <a name="ss-ownership"></a>GSL.owner: Pointeurs de propriété

* `unique_ptr<T>`     // propriété unique : `std::unique_ptr<T>`
* `shared_ptr<T>`     // propriété partagée : `std::shared_ptr<T>` (pointeur compté)
* `stack_array<T>`    // Un tableau alloué sur la pile. Le nombre d'éléments est déterminé à la construction et fixe par la suite. Les éléments sont mutables à moins que `T` ne soit un type `const`.
* `dyn_array<T>`      // Un conteneur, tableau alloué dynamiquement non croissant. Le nombre d'éléments est déterminé à la construction et fixe par la suite.  
    Les éléments sont mutables à moins que `T` ne soit un type `const`. Essentiellement un `span` qui alloue et possède ses éléments.

## <a name="ss-assertions"></a>GSL.assert: Assertions

* `Expects`     // assertion de précondition. Actuellement placée dans les corps de fonction. Plus tard, devrait être déplacée vers les déclarations.  
                // `Expects(p)` termine le programme à moins que `p == true`  
                // `Expects` est sous le contrôle de certaines options (exécution, message d'erreur, alternatives à la terminaison)
* `Ensures`     // assertion de postcondition. Actuellement placée dans les corps de fonction. Plus tard, devrait être déplacée vers les déclarations.

Ces assertions sont actuellement des macros (détestable !) et doivent apparaître uniquement dans les définitions de fonctions, en attendant les décisions du comité standard sur les contrats et la syntaxe des assertions.  
Voir [la proposition de contrat](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0380r1.pdf) ; en utilisant la syntaxe d'attribut, par ex., `Expects(p)` deviendra `[[expects: p]]`.

## <a name="ss-utilities"></a>GSL.util: Utilitaires

* `finally`        // `finally(f)` crée un `final_action{f}` dont le destructeur invoque `f`
* `narrow_cast`    // `narrow_cast<T>(x)` est `static_cast<T>(x)`
* `narrow`         // `narrow<T>(x)` est `static_cast<T>(x)` si `static_cast<T>(x) == x` sans promotions de signe, sinon il lance `narrowing_error` (par ex., `narrow<unsigned>(-42)` lance)
* `[[implicit]]`   // "Marqueur" à mettre sur les constructeurs à un seul argument pour les rendre explicitement non-explicit
* `move_owner`     // `p = move_owner(q)` signifie `p = q` mais ???
* `joining_thread` // une version RAII de `std::thread` qui joint.
* `index`          // un type à utiliser pour l'indexation de tous les conteneurs et tableaux (actuellement un alias de `ptrdiff_t`)

## <a name="ss-gsl-concepts"></a>GSL.concept: Concepts

Ces concepts (prédicats de type) sont empruntés à la bibliothèque Origin d'Andrew Sutton, à la proposition Range et au TR ISO WG21 Palo Alto.  
Beaucoup d'entre eux sont très similaires à ce qui est devenu partie de la norme ISO C++ dans C++20.

* `String`
* `Number`
* `Boolean`
* `Range`              // en C++20, `std::ranges::range`
* `Sortable`           // en C++20, `std::sortable`
* `EqualityComparable` // en C++20, `std::equality_comparable`
* `Convertible`        // en C++20, `std::convertible_to`
* `Common`             // en C++20, `std::common_with`
* `Integral`           // en C++20, `std::integral`
* `SignedIntegral`     // en C++20, `std::signed_integral`
* `SemiRegular`        // en C++20, `std::semiregular`
* `Regular`            // en C++20, `std::regular`
* `TotallyOrdered`     // en C++20, `std::totally_ordered`
* `Function`           // en C++20, `std::invocable`
* `RegularFunction`    // en C++20, `std::regular_invocable`
* `Predicate`          // en C++20, `std::predicate`
* `Relation`           // en C++20, `std::relation`
* ...

### <a name="ss-gsl-smartptrconcepts"></a>GSL.ptr: Concepts de pointeurs intelligents

* `Pointer`  // Un type avec `*`, `->`, `==`, et construction par défaut (la construction par défaut est supposée définir la valeur "null" unique)
* `Unique_pointer`  // Un type qui correspond à `Pointer`, est déplaçable, et n'est pas copiable
* `Shared_pointer`   // Un type qui correspond à `Pointer`, et est copiable
