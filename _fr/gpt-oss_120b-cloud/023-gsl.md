# <a name="s-gsl"></a>GSL : Bibliothèque de support aux directives

La GSL est une petite bibliothèque de fonctionnalités conçues pour soutenir cet ensemble de directives. Sans ces fonctionnalités, les directives devraient être beaucoup plus restrictives sur les détails du langage.

La bibliothèque de support des Core Guidelines est définie dans l’espace de noms `gsl` et les noms peuvent être des alias de la bibliothèque standard ou d’autres bibliothèques bien connues. L’utilisation de l’indirection (au moment de la compilation) via l’espace de noms `gsl` permet l’expérimentation ainsi que la création de variantes locales des fonctionnalités de support.

La GSL est une bibliothèque uniquement d’en‑têtes, et se trouve à l’adresse [GSL: Guidelines support library](https://github.com/Microsoft/GSL). Les fonctionnalités de la bibliothèque de support sont conçues pour être extrêmement légères (sans frais d’exécution) de sorte qu’elles n’imposent aucun surcoût par rapport à l’utilisation d’alternatives classiques. Lorsqu’on le souhaite, elles peuvent être « instrumentées » avec des fonctionnalités supplémentaires (par ex. : des vérifications) pour des tâches telles que le débogage.

Ces Directives utilisent des types de la bibliothèque standard (par ex. : C++17) en plus de ceux provenant de la GSL. Par exemple, nous supposons l’existence d’un type `variant`, mais celui‑ci n’est pas encore présent dans la GSL. Au final, utilisez [celui qui a été intégré à C++17](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0088r3.html).

Certains des types GSL répertoriés ci‑dessous peuvent ne pas être pris en charge par la bibliothèque que vous utilisez en raison de contraintes techniques, comme les limites des versions actuelles de C++. Par conséquent, veuillez consulter la documentation de votre GSL pour en savoir davantage.

Pour chaque type GSL ci‑dessous, nous indiquons une invariant pour ce type. Cette invariant est valable tant que le code utilisateur ne modifie l’état d’un objet GSL qu’en utilisant les fonctions membres ou libres fournies par le type (c’est‑à‑dire que le code utilisateur ne contourne pas l’interface du type pour changer la valeur/les bits de l’objet en violant une autre règle des Directives).

## <a name="ss-views"></a>GSL.view : Vues

Ces types permettent à l’utilisateur de distinguer les pointeurs propriétaires des pointeurs non‑propriétaires, ainsi que les pointeurs vers un seul objet des pointeurs vers le premier élément d’une séquence.

Ces « vues » ne sont jamais propriétaires.

Les références ne sont jamais propriétaires (voir [R.4](009-resource.md#rr-ref)). @TODO-LINK  
Remarque : les références peuvent facilement dépasser la durée de vie des objets auxquels elles font référence (renvoyer une variable locale par référence, conserver une référence à un élément d’un vecteur puis appeler `push_back`, se lier à `std::max(x, y + 1)`, etc.). Le profil de sécurité de durée de vie vise à traiter ces cas, mais même ainsi, `owner<T&>` n’a pas de sens et est découragé.

Les noms sont principalement du style de la bibliothèque standard (minuscules et séparateurs de soulignement) :

    T*      // Le `T*` n’est pas propriétaire, peut être nul ; on suppose qu’il pointe vers un seul élément.
    T&      // Le `T&` n’est pas propriétaire et ne peut jamais être une « référence nulle » ; les références sont toujours liées à des objets.

La notation « pointeur brut » (p. ex. `int*`) est supposée avoir son sens le plus courant ; c’est‑à‑dire qu’un pointeur pointe vers un objet, mais n’en est pas propriétaire.

Les propriétaires devraient être convertis en gestionnaires de ressources (p. ex. `std::unique_ptr` ou `std::vector<T>`) ou marqués `owner<T*>`.

    owner<T*>   // un `T*` qui possède l’objet pointé/référencé ; peut être `nullptr`.

`owner` est utilisé pour marquer les pointeurs propriétaires dans du code qui ne peut pas être migré vers l’utilisation de véritables gestionnaires de ressources. Les raisons incluent :

* Coût de la conversion.  
* Le pointeur est utilisé avec une ABI.  
* Le pointeur fait partie de l’implémentation d’un gestionnaire de ressources.

Un `owner<T>` diffère d’un gestionnaire de ressource pour un `T` en ce qu’il nécessite toujours un `delete` explicite.

Un `owner<T>` est supposé référencer un objet sur le tas (heap).

Si quelque chose ne doit pas être `nullptr`, indiquez‑le :

    not_null<T>   // `T` est généralement un type pointeur (p. ex. `not_null<int*>` et `not_null<owner<Foo*>>`) qui ne doit jamais être `nullptr`. `T` peut être tout type pour lequel `==nullptr` a du sens.

    span<T>        // `[p:p+n)`, constructeur depuis `{p, q}` et `{p, n}` ; `T` est le type de pointeur  
    span_p<T>      // `{p, predicate}` `[p:q)` où `q` est le premier élément pour lequel `predicate(*p)` vaut vrai

Un `span<T>` désigne zéro ou plusieurs `T` mutables, à moins que `T` ne soit de type `const`. Tous les accès aux éléments du span, notamment via `operator[]`, sont garantis d’être contrôlés par rapport aux limites par défaut.

> Note : le `span` de la GSL (initialement appelé `array_view`) a été proposé pour être intégré dans la bibliothèque standard C++, et a été adopté (avec des changements de nom et d’interface) à l’exception du fait que `std::span` ne fournit pas de garantie de contrôle des limites. Ainsi, la GSL a modifié le nom et l’interface du `span` pour suivre `std::span` et il doit être exactement identique à `std::span`, la seule différence étant que le `span` de la GSL assure pleinement la sécurité des limites par défaut. Si la sûreté des limites devait impacter son interface, ces propositions de modification devraient être repoussées via le comité ISO C++ afin que `gsl::span` reste compatible au niveau de l’interface avec `std::span`. Si une évolution future de `std::span` ajoute le contrôle des limites, `gsl::span` pourra être supprimé.

L’arithmétique de pointeurs est préférable à l’intérieur des `span`s.

Un `char*` qui pointe vers plus d’un `char` mais ne représente pas une chaîne de caractères de style C (p. ex. : un pointeur dans un tampon d’entrée) devrait être représenté par un `span`.

    zstring    // un `char*` censé être une chaîne de caractères de style C ; c’est‑à‑dire une séquence de `char` terminée par zéro ou `nullptr`
    czstring   // un `const char*` censé être une chaîne de caractères de style C ; c’est‑à‑dire une séquence de `const char` terminée par zéro ou `nullptr`

Logiquement, ces deux derniers alias ne sont pas nécessaires, mais nous ne sommes pas toujours logiques, et ils rendent explicite la distinction entre un pointeur vers un seul `char` et un pointeur vers une chaîne de caractères de style C.

Une séquence de caractères dont on ne suppose pas qu’elle se termine par zéro devrait être un `span<char>`, ou, si cela est impossible à cause de problèmes d’ABI, un `char*`, plutôt qu’un `zstring`.

## <a name="ss-assertions"></a>GSL.assert : Assertions

    Expects   // assertion de précondition. Placée actuellement dans les corps de fonction. Plus tard, elle devrait être déplacée dans les déclarations.
              // `Expects(p)` termine le programme à moins que `p == true`
              // `Expects` dépend de certaines options (application, message d’erreur, alternatives à la terminaison)
    Ensures   // assertion de postcondition. Placée actuellement dans les corps de fonction. Plus tard, elle devrait être déplacée dans les déclarations.

Ces assertions sont actuellement des macros (beurk !) et doivent apparaître dans les définitions de fonctions (seulement) en attente des décisions du comité de normalisation sur les contrats et la syntaxe des assertions.

Voir [la proposition de contrat](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0380r1.pdf) ; en utilisant la syntaxe d’attribut, par exemple, `Expects(p)` deviendra `[[expects: p]]`.

## <a name="ss-gsl-concepts"></a>GSL.concept : Concepts

Ces concepts (prédicats de type) sont empruntés à la bibliothèque Origin d’Andrew Sutton, à la proposition Range, et au TR ISO WG21 Palo Alto. Beaucoup d’entre eux sont très similaires à ce qui a été intégré dans la norme ISO C++ en C++20.

* `String`
* `Number`
* `Boolean`
* `Range`              // en C++20, `std::ranges::range`
* `Sortable`           // en C++20, `std::sortable`
* `EqualityComparable` // en C++20, `std::equality_comparable`
* `Convertible`        // en C++20, `std::convertible_to`
* `Common`             // en C++20, `std::common_with`
* `Integral`           // en C++20, `std::integral`
* `SignedIntegral`     // en C++20, `std::signed_integral`
* `SemiRegular`        // en C++20, `std::semiregular`
* `Regular`            // en C++20, `std::regular`
* `TotallyOrdered`     // en C++20, `std::totally_ordered`
* `Function`           // en C++20, `std::invocable`
* `RegularFunction`    // en C++20, `std::regular_invocable`
* `Predicate`          // en C++20, `std::predicate`
* `Relation`           // en C++20, `std::relation`
* ...

### <a name="ss-gsl-smartptrconcepts"></a>GSL.ptr : Concepts de pointeur intelligent

    Pointer            // Un type avec `*`, `->`, `==` et construction par défaut (la construction par défaut est supposée établir la valeur singulière « null »)
    Unique_pointer    // Un type qui correspond à `Pointer`, est déplaçable, et n’est pas copiable
    Shared_pointer    // Un type qui correspond à `Pointer`, et est copiable
