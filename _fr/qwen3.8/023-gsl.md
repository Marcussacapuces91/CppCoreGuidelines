# <a name="s-gsl"></a>GSL : Guidelines Support Library

La GSL est une petite bibliothèque de fonctionnalités conçue pour soutenir cet ensemble de lignes directrices.
Sans ces fonctionnalités, les lignes directrices devraient être beaucoup plus restrictives quant aux détails du langage.

La bibliothèque de support des Lignes Directrices est définie dans l'espace de noms `gsl` et les noms peuvent être des alias pour des noms de la bibliothèque standard ou d'autres bibliothèques bien connues. L'utilisation de l'indirection (à la compilation) via l'espace de noms `gsl` permet l'expérimentation et les variantes locales des fonctionnalités de support.

La GSL est une bibliothèque « header-only » (uniquement des en-têtes) et peut être trouvée sur [GSL : Guidelines Support Library](https://github.com/Microsoft/GSL).
Les fonctionnalités de la bibliothèque de support sont conçues pour être extrêmement légères (zéro surcoût) afin de ne pas imposer de surcoût par rapport à l'utilisation d'alternatives conventionnelles.
Lorsque c'est souhaitable, elles peuvent être « instrumentées » avec des fonctionnalités supplémentaires (par exemple, des vérifications) pour des tâches telles que le débogage.

Ces Lignes Directrices utilisent des types de la norme (par exemple, C++17) en plus de ceux de la GSL.
Par exemple, nous supposons un type `variant`, mais celui-ci n'est pas actuellement présent dans la GSL.
À terme, utilisez [celui qui a été voté pour C++17](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0088r3.html).

Certains des types GSL listés ci-dessous peuvent ne pas être pris en charge par la bibliothèque que vous utilisez, pour des raisons techniques telles que les limitations des versions actuelles de C++.
Veuillez donc consulter la documentation de votre GSL pour en savoir plus.

Pour chaque type GSL ci-dessous, nous énonçons un invariant pour ce type. Cet invariant est valable tant que le code utilisateur ne modifie l'état d'un objet GSL qu'en utilisant les fonctions membres/libres fournies par le type (c'est-à-dire que le code utilisateur ne contourne pas l'interface du type pour modifier la valeur/les bits de l'objet en violant toute autre règle des Lignes Directrices).

Nous prévoyons une spécification semi-formelle de la GSL dans le style « ISO C++ standard ».

Nous nous appuyons sur la bibliothèque standard ISO C++ et espérons qu'une partie de la GSL soit intégrée à la bibliothèque standard.

## <a name="ss-views"></a>GSL.view : Vues

Ces types permettent à l'utilisateur de distinguer entre les pointeurs propriétaires et non propriétaires, et entre les pointeurs vers un objet unique et les pointeurs vers le premier élément d'une séquence.

Ces « vues » ne sont jamais propriétaires.

Les références ne sont jamais propriétaires (voir [R.4](009-resource.md#rr-ref)). Remarque : les références ont de nombreuses occasions de survivre aux objets auxquels elles font référence (retourner une variable locale par référence, conserver une référence vers un élément d'un vecteur et effectuer `push_back`, lier à `std::max(x, y + 1)`, etc.). Le profil de sécurité de durée de vie vise à traiter ces problèmes, mais même ainsi `owner<T&>` n'a pas de sens et est déconseillé.

Les noms sont principalement au style de la bibliothèque standard ISO (minuscules et tirets bas) :

    T*      // Le T* n'est pas un propriétaire, peut être nul ; supposé pointer vers un seul élément.
    T&      // Le T& n'est pas un propriétaire et ne peut jamais être une « référence nulle » ; les références sont toujours liées à des objets.

La notation « pointeur brut » (par exemple `int*`) est supposée avoir sa signification la plus courante ; c'est-à-dire qu'un pointeur pointe vers un objet, mais ne lui appartient pas.
Les propriétaires doivent être convertis en descripteurs de ressources (par exemple `unique_ptr` ou `vector<T>`) ou marqués `owner<T*>`.

    owner<T*>   // un T* qui possède l'objet pointé/référencé ; peut être nullptr.

`owner` est utilisé pour marquer les pointeurs propriétaires dans du code qui ne peut pas être mis à niveau pour utiliser de vrais descripteurs de ressources.
Les raisons incluent :

* Le coût de la conversion.
* Le pointeur est utilisé avec une ABI.
* Le pointeur fait partie de l'implémentation d'un descripteur de ressource.

Un `owner<T>` diffère d'un descripteur de ressource pour un `T` par le fait qu'il requiert encore un `delete` explicite.

Un `owner<T>` est supposé référencer un objet dans la zone de stockage libre (tas).

Si quelque chose ne doit pas être `nullptr`, dites-le :

    not_null<T>   // T est généralement un type pointeur (par exemple not_null<int*> et not_null<owner<Foo*>>) qui ne doit pas être nullptr.
                  // T peut être n'importe quel type pour lequel ==nullptr est significatif.

    span<T>       // [p:p+n), constructeur depuis {p, q} et {p, n} ; T est le type pointeur
    span_p<T>     // {p, prédicat} [p:q) où q est le premier élément pour lequel prédicat(*p) est vrai

Un `span<T>` référence zéro ou plusieurs `T` mutables, sauf si `T` est un type `const`. Tous les accès aux éléments de la vue, notamment via `operator[]`, sont garantis d'être vérifiés par rapport aux limites par défaut.

> Remarque : la `span` de la GSL (initialement appelée `array_view`) a été proposée pour inclusion dans la bibliothèque standard C++, et a été adoptée (avec des modifications de son nom et de son interface), à l'exception du fait que `std::span` ne fournit pas de vérification des limites garantie. Par conséquent, la GSL a modifié le nom et l'interface de `span` pour suivre `std::span` et devrait être exactement identique à `std::span`, et la seule différence devrait être que la `span` de la GSL est entièrement sûre par rapport aux limites par défaut. Si la sécurité des limites pourrait affecter son interface, alors ces propositions de modification devraient être soumises au comité ISO C++ pour maintenir la compatibilité d'interface entre `gsl::span` et `std::span`. Si une évolution future de `std::span` ajoute la vérification des limites, `gsl::span` pourra être supprimée.

L'« arithmétique de pointeurs » est préférablement effectuée dans des `span`.
Un `char*` qui pointe vers plus d'un `char` mais qui n'est pas une chaîne au style C (par exemple, un pointeur dans un tampon d'entrée) devrait être représenté par une `span`.

    zstring    // un char* supposé être une chaîne au style C ; c'est-à-dire une séquence de char terminée par zéro ou nullptr
    czstring   // un const char* supposé être une chaîne au style C ; c'est-à-dire une séquence de const char terminée par zéro ou nullptr

Logiquement, ces deux derniers alias ne sont pas nécessaires, mais nous ne sommes pas toujours logiques, et ils rendent la distinction entre un pointeur vers un seul `char` et un pointeur vers une chaîne au style C explicite.
Une séquence de caractères qui n'est pas supposée être terminée par zéro devrait être une `span<char>`, ou si c'est impossible à cause de problèmes d'ABI, un `char*`, plutôt qu'un `zstring`.

## <a name="ss-ownership"></a>GSL.owner : Pointeurs de propriété

    unique_ptr<T>     // propriété exclusive : std::unique_ptr<T>
    shared_ptr<T>     // propriété partagée : std::shared_ptr<T> (un pointeur compté)
    stack_array<T>    // Un tableau alloué sur la pile. Le nombre d'éléments est déterminé à la construction et fixe par la suite.
                      // Les éléments sont mutables sauf si T est un type const.
    dyn_array<T>      // Un conteneur, tableau alloué dynamiquement non extensible. Le nombre d'éléments est déterminé à la construction et fixe par la suite.
                      // Les éléments sont mutables sauf si T est un type const. En gros, une span qui alloue et possède ses éléments.

## <a name="ss-assertions"></a>GSL.assert : Assertions

    Expects     // assertion de précondition. Actuellement placée dans les corps de fonctions. Plus tard, devrait être déplacée dans les déclarations.
                // Expects(p) termine le programme sauf si p == true
                // Expects est sous le contrôle de certaines options (application, message d'erreur, alternatives à la terminaison)
    Ensures     // assertion de postcondition. Actuellement placée dans les corps de fonctions. Plus tard, devrait être déplacée dans les déclarations.

Ces assertions sont actuellement des macros (pourtant !) et doivent apparaître dans les définitions de fonctions (uniquement)
en attendant les décisions du comité de normalisation sur les contrats et la syntaxe des assertions.
Voir [la proposition de contrats](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2016/p0380r1.pdf) ; en utilisant la syntaxe d'attribut,
par exemple, `Expects(p)` deviendra `[[expects: p]]`.

    finally        // finally(f) crée un final_action{f} avec un destructeur qui invoque f
    narrow_cast    // narrow_cast<T>(x) est static_cast<T>(x)

## <a name="ss-gsl-concepts"></a>GSL.concept : Concepts

Ces concepts (prédicats de types) sont empruntés à
la bibliothèque Origin d'Andrew Sutton,
à la proposition Range,
et au TR de Palo Alto du WG21 ISO.
Beaucoup d'entre eux sont très similaires à ce qui est devenu partie de la norme ISO C++ dans C++20.

    String
    Number
    Boolean
    Range              // en C++20, std::ranges::range
    Sortable           // en C++20, std::sortable
    EqualityComparable // en C++20, std::equality_comparable
    Convertible        // en C++20, std::convertible_to
    Common             // en C++20, std::common_with
    Integral           // en C++20, std::integral
    SignedIntegral     // en C++20, std::signed_integral
    SemiRegular        // en C++20, std::semiregular
    Regular            // en C++20, std::regular
    TotallyOrdered     // en C++20, std::totally_ordered
    Function           // en C++20, std::invocable
    RegularFunction    // en C++20, std::regular_invocable
    Predicate          // en C++20, std::predicate
    Relation           // en C++20, std::relation
    ...
