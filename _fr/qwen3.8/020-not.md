# <a name="s-not"></a>NR : Non-règles et mythes

Cette section contient des règles et des directives populaires en certains endroits, mais que nous ne recommandons délibérément pas.
Nous savons parfaitement qu'il y a eu des époques et des contextes où ces règles avaient du sens, et nous les avons nous-mêmes utilisées à certaines occasions.
Cependant, dans le contexte des styles de programmation que nous recommandons et soutenons à travers ces lignes directrices, ces « non-règles » seraient préjudiciables.

Même aujourd'hui, il peut exister des contextes où ces règles ont du sens.
Par exemple, le manque d'outils adaptés peut rendre les exceptions inadaptées dans les systèmes temps réel dur,
mais ne vous fiez pas naïvement au « bon sens » (par exemple, des affirmations non étayées sur l'« efficacité ») ;
une telle « sagesse » pourrait être basée sur des informations datant de plusieurs décennies ou sur des expériences issues de langages aux propriétés très différentes de celles de C++
(par exemple, C ou Java).

Les arguments positifs en faveur des alternatives à ces non-règles sont listés dans les règles proposées en tant qu'« Alternatives ».

### <a name="rnr-top"></a>NR.1 : Ne pas imposer que toutes les déclarations soient en tête de fonction

##### Raison

La règle « toutes les déclarations en haut » est un héritage des anciens langages de programmation qui ne permettaient pas l'initialisation de variables et de constantes après une instruction.
Cela conduit à des programmes plus longs et à plus d'erreurs causées par des variables non initialisées ou mal initialisées.

##### Exemple, mauvais

    int use(int x)
    {
        int i;
        char c;
        double d;

        // ... quelques opérations ...

        if (x < i) {
            // ...
            i = f(x, d);
        }
        if (i < x) {
            // ...
            i = g(x, c);
        }
        return i;
    }

Plus la distance entre la variable non initialisée et son utilisation est grande, plus la probabilité d'un bug est élevée.
Heureusement, les compilateurs détectent de nombreuses erreurs de « utilisation avant initialisation ».
Malheureusement, les compilateurs ne peuvent pas détecter toutes ces erreurs et, malheureusement, les bugs ne sont pas toujours aussi faciles à repérer que dans cet exemple réduit.

* [Toujours initialiser un objet](010-expr.md#res-always) @TODO-LINK

### <a name="rnr-single-return"></a>NR.2 : Ne pas imposer d'avoir une seule instruction `return` dans une fonction

##### Raison

La règle du retour unique peut conduire à un code inutilement contorsionné et à l'introduction de variables d'état supplémentaires.
En particulier, la règle du retour unique rend plus difficile la concentration des vérifications d'erreurs en tête de fonction.

##### Exemple

    template<class T>
    //  requires Number<T>
    string sign(T x)
    {
        if (x < 0)
            return "negative";
        if (x > 0)
            return "positive";
        return "zero";
    }

Pour n'utiliser qu'un seul `return`, il faudrait faire quelque chose comme

    template<class T>
    //  requires Number<T>
    string sign(T x)        // mauvais
    {
        string res;
        if (x < 0)
            res = "negative";
        else if (x > 0)
            res = "positive";
        else
            res = "zero";
        return res;
    }

C'est à la fois plus long et probablement moins efficace.
Plus la fonction est grande et complexe, plus les contournements deviennent pénibles.
Bien sûr, de nombreuses fonctions simples auront naturellement un seul `return` en raison de leur logique intrinsèquement plus simple.

##### Exemple

    int index(const char* p)
    {
        if (!p) return -1;  // indicateur d'erreur : alternativement "throw nullptr_error{}"
        // ... effectuer une recherche pour trouver l'index de p
        return i;
    }

Si nous appliquions la règle, nous obtiendrions quelque chose comme

    int index2(const char* p)
    {
        int i;
        if (!p)
            i = -1;  // indicateur d'erreur
        else {
            // ... effectuer une recherche pour trouver l'index de p
        }
        return i;
    }

Notez que nous (délibérément) avons violé la règle contre les variables non initialisées, car ce style conduit couramment à cela.
De plus, ce style est une tentation d'utiliser la non-règle [goto exit](020-not.md#rnr-goto-exit).

##### Alternative

* Garder les fonctions courtes et simples
* N'hésitez pas à utiliser plusieurs instructions `return` (et à lever des exceptions).

### <a name="rnr-no-exceptions"></a>NR.3 : Ne pas éviter les exceptions

##### Raison

Il semble qu'il y ait quatre raisons principales avancées pour ne pas utiliser les exceptions :

* les exceptions sont inefficaces
* les exceptions conduisent à des fuites et des erreurs
* les performances des exceptions ne sont pas prévisibles
* le support d'exécution de la gestion des exceptions occupe trop de place

Il n'y a aucun moyen de trancher cette question à la satisfaction de tout le monde.
Après tout, les discussions sur les exceptions durent depuis plus de 40 ans.
Certains langages ne peuvent pas être utilisés sans exceptions, mais d'autres ne les supportent pas.
Cela engendre de fortes traditions pour l'usage et la non-utilisation des exceptions, ainsi que des débats passionnés.

Cependant, nous pouvons brièvement esquisser pourquoi nous considérons les exceptions comme la meilleure alternative pour la programmation générale
et dans le contexte de ces lignes directrices.
Les arguments simples pour et contre sont souvent inconclusifs.
Il existe des applications spécialisées où les exceptions peuvent effectivement être inappropriées
(par exemple, les systèmes temps réel dur sans support pour des estimations fiables du coût du traitement d'une exception).

Considérons les principales objections aux exceptions tour à tour :

* Les exceptions sont inefficaces :
Par rapport à quoi ?
Lors de la comparaison, assurez-vous que le même ensemble d'erreurs est géré et qu'elles sont gérées de manière équivalente.
En particulier, ne comparez pas un programme qui se termine immédiatement à la détection d'une erreur à un programme
qui nettoie soigneusement les ressources avant de consigner une erreur.
Oui, certains systèmes ont des implémentations de gestion des exceptions médiocres ; parfois, de telles implémentations nous obligent à utiliser
d'autres approches de gestion d'erreurs, mais ce n'est pas un problème fondamental des exceptions.
Lorsque vous utilisez un argument d'efficacité — dans n'importe quel contexte —, assurez-vous d'avoir de bonnes données qui fournissent
vraiment des éclaircissements sur le problème discuté.
* Les exceptions conduisent à des fuites et des erreurs.
Ce n'est pas le cas.
Si votre programme est un enchevêtrement de pointeurs sans stratégie globale de gestion des ressources,
vous avez un problème quoi que vous fassiez.
Si votre système consiste en un million de lignes de tel code,
vous ne pourrez probablement pas utiliser les exceptions,
mais c'est un problème lié à l'usage excessif et indiscipliné des pointeurs, plutôt qu'aux exceptions.
À notre avis, vous avez besoin du RAII pour rendre la gestion d'erreurs basée sur les exceptions simple et sûre — plus simple et plus sûre que les alternatives.
* Les performances des exceptions ne sont pas prévisibles.
Si vous êtes dans un système temps réel dur où vous devez garantir l'achèvement d'une tâche dans un temps donné,
vous avez besoin d'outils pour étayer de telles garanties.
À notre connaissance, de tels outils ne sont pas disponibles (du moins pas pour la plupart des programmeurs).
* Le support d'exécution de la gestion des exceptions occupe trop de place.
Cela peut être le cas dans les petits systèmes (généralement embarqués).
Cependant, avant d'abandonner les exceptions, considérez l'espace que nécessiterait une gestion d'erreurs cohérente à l'aide de codes d'erreur
et le coût d'une erreur non détectée.

Beaucoup, peut-être la plupart, des problèmes liés aux exceptions découlent de besoins historiques d'interaction avec du code ancien et désordonné.

Les arguments fondamentaux en faveur de l'utilisation des exceptions sont :

* Elles distinguent clairement le retour en erreur du retour ordinaire
* Elles ne peuvent pas être oubliées ou ignorées
* Elles peuvent être utilisées de manière systématique

À retenir :

* Les exceptions servent à signaler des erreurs (en C++ ; d'autres langages peuvent avoir des usages différents pour les exceptions).
* Les exceptions ne sont pas destinées aux erreurs qui peuvent être gérées localement.
* N'essayez pas de capturer chaque exception dans chaque fonction (c'est fastidieux, maladroit et conduit à un code lent).
* Les exceptions ne sont pas destinées aux erreurs qui nécessitent la terminaison immédiate d'un module/système après une erreur non récupérable.

### <a name="rnr-two-phase-init"></a>NR.5 : Ne pas utiliser l'initialisation en deux phases

##### Raison

Diviser l'initialisation en deux phases conduit à des invariants plus faibles,
à un code plus complexe (il faut gérer des objets partiellement construits),
et à des erreurs (lorsque nous n'avons pas correctement géré les objets partiellement construits de manière cohérente).

##### Note

Parfois également appelé construction en deux étapes.

##### Exemple, mauvais

    // Ancien style conventionnel : de nombreux problèmes

    class Picture
    {
        int mx;
        int my;
        int * data;
    public:
        // problème principal : le constructeur ne construit pas complètement
        Picture(int x, int y)
        {
            mx = x;         // également mauvais : affectation dans le corps du constructeur
                            // plutôt que dans l'initialiseur de membre
            my = y;
            data = nullptr; // également mauvais : initialisation constante dans le constructeur
                            // plutôt que dans l'initialiseur de membre
        }

        ~Picture()
        {
            Cleanup();
        }

        // ...

        // mauvais : initialisation en deux phases
        bool Init()
        {
            // vérification des invariants
            if (mx <= 0 || my <= 0) {
                return false;
            }
            if (data) {
                return false;
            }
            data = (int*) malloc(mx*my*sizeof(int));   // également mauvais : pointeur brut propriétaire et malloc
            return data != nullptr;
        }

        // également mauvais : aucune raison de faire du nettoyage une fonction séparée
        void Cleanup()
        {
            if (data) free(data);
            data = nullptr;
        }
    };

    Picture picture(100, 0); // pas d'image prête à l'emploi ici
    // cela va échouer...
    if (!picture.Init()) {
        puts("Error, invalid picture");
    }
    // maintenant nous avons une instance d'objet image invalide.

##### Exemple, bon

    class Picture
    {
        int mx;
        int my;
        vector<int> data;

        static int check_size(int size)
        {
            // vérification de l'invariant
            Expects(size > 0);
            return size;
        }

    public:
        // encore mieux serait une classe pour une Taille 2D en tant que paramètre unique
        Picture(int x, int y)
            : mx(check_size(x))
            , my(check_size(y))
            // maintenant nous savons que x et y ont une taille valide
            , data(mx * my) // lèvera std::bad_alloc en cas d'erreur
        {
            // l'image est prête à l'emploi
        }

        // le destructeur généré par le compilateur fait le travail. (voir aussi C.21)

        // ...
    };

    Picture picture1(100, 100);
    // picture1 est prête à l'emploi ici...

    // taille invalide pour y,
    // le comportement par défaut de violation de contrat appellera std::terminate
    Picture picture2(100, 0);
    // on n'atteindra pas ici...

##### Alternative

* Établissez toujours un invariant de classe dans un constructeur.
* Ne définissez pas un objet avant qu'il ne soit nécessaire.

### <a name="rnr-goto-exit"></a>NR.6 : Ne pas regrouper toutes les actions de nettoyage en fin de fonction avec `goto exit`

##### Raison

`goto` est source d'erreurs.
Cette technique est une technique pré-exceptions pour la gestion des ressources et des erreurs de type RAII.

##### Exemple, mauvais

    void do_something(int n)
    {
        if (n < 100) goto exit;
        // ...
        int* p = (int*) malloc(n);
        // ...
        if (some_error) goto exit;
        // ...
    exit:
        free(p);
    }

et repérez le bug.

##### Alternative

* Utilisez les exceptions et le [RAII](013-errors.md#re-raii) @TODO-LINK
* pour les ressources non-RAII, utilisez [`finally`](013-errors.md#re-finally) @TODO-LINK.

### <a name="rnr-protected-data"></a>NR.7 : Ne pas rendre les membres de données `protected`

##### Raison

Les données `protected` sont une source d'erreurs.
Les données `protected` peuvent être manipulées depuis une quantité illimitée de code à divers endroits.
Les données `protected` sont l'équivalent dans la hiérarchie de classes des données globales.
